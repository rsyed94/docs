Open in Passport: [Rules](https://passportmcp.com/#rules)

Autopilot decides every action your agents take through Passport, instantly, from your rules. It asks you only when a rule says so, and every decision names its cause, such as "Asked: Production changes ask first (Careful)."

## How a decision is made

Every action is decided the same way, whether it's a tool call, a command through the CLI guard, or `passport exec`. The first step that applies decides:

1. **Access**: what you may do with the app, set on its **Access** tab, and whether an admin switched the tool off. **No access** blocks everything; **Read-only** runs only reads. No exception or preset gets past it.
2. **Exceptions**: a block always wins, then the most specific exception.
3. **Team floors**: your team's minimum preset for that environment. An exception can't be looser than it.
4. **Your preset** for the environment.

An irreversible action always asks unless an exception names that exact action. **Test a command** on the **Rules** page answers in the same order, so an access block shows its cause with a link to the app's **Access** tab.

An app's **Tools** tab shows the answer for each tool before any agent calls it: **Allowed**, **Asks first**, or **Withheld**, with the reason, such as "Your access is Read-only". A withheld tool has one control, **Request access**, when a request can lift it: **Full access** for a Read-only pass, or an exception for a team or workspace rule. Once filed, it reads **Requested** and links to your [Inbox](/member/inbox#your-requests). See [Status words](/concepts/status-words).

## Actions and environments

Each action is one of four classes:

- **Read**: looks at something.
- **Change**: creates or edits.
- **Delete**: removes or overwrites. Rollbacks, secret changes, and schema migrations count.
- **Irreversible**: can't be taken back even with a backup: sending money or email, force-pushing the default branch, deleting a repository.

Each action also runs in an environment: **Production**, **Staging**, or **Development**. Passport reads it from the action, such as a Railway environment, a Vercel target, a Supabase project or branch, a Neon branch, or a CLI flag like `--environment`. When an agent names a resource only by its id, Passport asks that app once, with your own connection and only its read tools, and places the resource when the app's own facts are clear: a Railway environment's name or pull request environment, a Supabase default or preview branch, a Neon default branch, or a Vercel environment type. If an app has environments but Passport can't place the resource, it counts as Production, and the decision says so. Repository work lands where it goes: `gh` and `git` reads have no environment, a branch is Development, and code that reaches a repository's default branch counts as Production until you place that repository in [Rules › Environments](https://passportmcp.com/#rules?section=environments): Production if it deploys on merge, Staging if it doesn't. Local work, such as installs, builds, and tests, has no environment of its own. [Sessions](/member/sessions#where-an-action-lands) shows where each action landed and counts unplaced actions apart from confirmed Production.

Apps without environments, like Linear, Notion, and Slack, are **Other apps**.

### How Passport knows

Passport places a command the way the vendor's own CLI picks where it goes. The first answer wins:

1. **A flag** on the command, such as `-e staging` or `--prod`.
2. **The folder's link**, such as `railway link`, `.vercel/project.json`, `supabase link`, or a `DATABASE_URL` in `.env`.
3. **The vendor's default**, such as `vercel deploy` going to Preview.
4. **Your workspace's choice** for that resource.
5. **Its name**: whole words like `prod`, `staging`, `qa`, `dev`, or `preview`. `domain` doesn't count as `main`.
6. **Nothing**: it counts as Production, and the decision says so.

Railway, Supabase, and Neon links hold an id. Once a resource is placed, the id decides: if the name in a link file differs from the one Passport saved, the environment was renamed, so it keeps its place and shows the new name. A name in a link file never makes anything looser: for an id nobody has placed, Passport asks your connected app for its real name and places it by that, so a linked Railway environment called `staging` is Staging. Until the app has named it, or when the name says nothing, it counts as Production until someone chooses. If a link file can't be read, the command counts as Production. A database URL is read only for its host: a local database is Development; Passport never sends or stores the URL, user, or password.

Each decision says how Passport knows: "Runs: Staging is Hands-off (linked in this folder)." In **Rules › Environments**, each resource shows where it came from: a linked folder, its name, what the app said (such as **Neon default branch**), or **Set by** whoever chose. **Needs attention** on Home lists only resources Passport couldn't place, one row per app: anyone can **Confirm all** to keep them Production, and an admin can choose each. When an approval is waiting on a resource nobody has placed, the request shows **This is: Production · Staging · Development**. Choosing saves it for the whole workspace and decides the action again, so it may run right away. Anyone can say Production; anything looser needs an admin. Changing an environment in Rules or with `passport env set` applies to new actions only: a request that's already waiting keeps the environment it was raised with.

Run `passport env` in a folder to see what Passport reads there. **Rules › Environments** lists a resource the first time an agent works in it, not when you connect the app.

### Project scripts

[Rules › Environments › Project scripts](https://passportmcp.com/#rules?section=scripts) lists what your workspace has said about project scripts the guard can't read on its own, such as `deploy.py`: its environment and class, who set it, and **Changed since set** when the script changed. It's a classification, like placing an environment: your presets and exceptions still decide. Add one with **Add script**, from a Session row's **Tell Passport what this does**, or with `passport actions add`. Anyone can say Production for a change or worse; anything looser is **Proposed** until an admin approves it. See [Scripts](/member/cli-hook#scripts).

## Presets

For each environment, and for Other apps, choose how much agents can do on their own:

|              | Careful | Balanced | Hands-off |
| ------------ | ------- | -------- | --------- |
| Reads        | Run     | Run      | Run       |
| Changes      | Ask     | Run      | Run       |
| Deletes      | Ask     | Ask      | Run       |
| Irreversible | Ask     | Ask      | Ask       |

The defaults are **Production: Careful**, **Staging: Balanced**, **Development: Hands-off**, and **Other apps: Balanced**. Irreversible actions always ask unless an exception allows that one action. Your team may require a minimum preset for an environment; you can always pick something stricter.

On Hands-off, a delete runs only when Passport can take a backup first; otherwise it asks: "Couldn't take a backup first, so Passport is asking." From the shell, the guard backs up everyday deletes on your computer first: `rm` in the project or your home folder (Claude Code), `git reset --hard`, `git clean`, dropped stashes, and branch deletes (see [Backups on your computer](/member/undo#backups-on-your-computer)), so those run. Others, such as `kubectl delete` or `rm` outside the project, ask. Deleting folders a build or an install makes again loses no work, so `rm -r` of them inside the project, or a `git clean -x` that removes only what's inside them, runs with nothing to back up and isn't counted as risky: `node_modules`, `dist`, `build`, `out`, `.next`, `.nuxt`, `.turbo`, `.cache`, `coverage`, `__pycache__`, `.pytest_cache`, `.gradle`, `target` (beside a `Cargo.toml` or `pom.xml`), `.venv` or `venv` (beside a requirements or `pyproject.toml` file), and `vendor` (beside a `composer.json` or `go.mod`). A folder git tracks anything in gets the usual backup instead. A `git clean -x` that removes those folders and other ignored files runs once Passport has backed up the others (**Backed up (build folders not backed up)**), and asks when they're too large to keep. To let them run in Development, Staging, or Other apps, turn on **Run deletes without a backup** for that row. An exception that runs deletes still runs them.

Each environment row also says what the CLI guard does **When Passport can't be reached**: **Ask**, **Block**, or **Run**. Every environment asks by default. An unattended agent or Codex can't ask, so Ask blocks there. Run never applies to irreversible actions or to anything your team requires. See [When Passport can't be reached](/member/cli-hook#when-passport-cant-be-reached).

What happened to an action reads **Ran**, **Asked**, or **Blocked** everywhere (and **Approved** or **Declined** for an approval). **Run**, **Ask**, and **Block** are what a preset or exception says to do.

## Exceptions

An exception runs, asks about, or blocks a specific action, an app, or a class of actions, in one environment or all of them. The most specific exception wins, the strictest wins among equals, and a block always wins. Admins can add exceptions for a team or everyone.

When an exception lets something run that your preset would ask about, Passport says so on the exception, such as "Deletes run in Production without asking, even without a backup.", and on each preset it loosens. The **Add exception** form shows the same warning before you save.

## The Rules page

**Rules** has a tab for your own rules (**Yours**), and for admins **Team** and, on Enterprise, [Data checks](/admin/data-checks). Every tab opens with one line saying what applies to you on top of your presets (admins see **Workspace safety** instead: floors, who approves Production deletes, Guard required, which agents can connect, the data check mode, and tools withheld for everyone, each linking to where it's set). **Yours** shows, in order: your presets, your exceptions, environments, and a one-line **Test a command**. [Rules › Team](https://passportmcp.com/#rules/team) holds **Team rules**, **Approval routing**, and **Which agents can connect**. Team rules give each team one line with its floors, whether Production deletes need someone else to approve, and whether it requires the guard, and a team’s **Access** tab shows the same line. Below them, **Approval routing** says who gets each team’s requests per environment, including who is on call; see [Approval routing](/admin/slack-and-approvers#approval-routing). Members see their own team’s line when it sets anything, such as "Production deletes need someone else to approve: Maya, on call." **Guard required** (Pro) stops `passport exec` for agents whose guard isn't on; see [Guard required](/member/cli-hook#guard-required).

## When Passport asks

When an action needs you, you can **Approve once**, **Approve for this session**, **Always allow** (which saves an exception), or **Decline** with a note the agent receives. Many agents show the question right where you are working; it is also waiting in your [Inbox](https://passportmcp.com/#inbox). If you turned notifications on, you can approve or decline from the notification.

### Confirm it's you

Approving a Production change or delete, or anything irreversible, takes a fresh check that it's you: Passport opens **Confirm it's you**, and you use your passkey or choose **Email me a code instead**. You add, rename, and remove passkeys in [Settings](https://passportmcp.com/#settings) under **Security**. These requests are approved in Passport only: Slack offers **Review in Passport**, and a phone notification opens the request. Your own agent's prompt can still approve a Production change you asked for at your keyboard, but never an irreversible action: the guard sends those to Passport. Declining never needs a check.

Saving a rule change that lets agents make Production changes with less checking takes the same check: an exception that runs or asks less in Production, removing a block or an ask, a looser Production preset, a lower team floor, turning off "someone else approves", approving an exception request, accepting a suggestion, placing an environment Passport treated as Production as Staging or Development, saying a Production project script is less risky (a lower class, or not Production), or moving someone off a team with a stricter Production floor (or deleting that team). Changes that tighten, or touch only Staging, Development, or reads, save as they are. The CLI and API can't show the check, so they're refused with a link to change it in Passport. Team changes from your identity provider (SCIM) are never blocked; when one loosens Production, the audit trail says so for an admin to review. A waiting request resolves itself from a rule change only when that change was confirmed.

### On your phone

Tapping a notification opens that request on its own screen: what the agent wants to do, where it lands, why Passport asked, and who is waiting, with **Approve** and **Decline** at the bottom of the screen. Approve is once; **More ways to approve** offers this session or **Always allow…**. After you answer, **Next request** opens the next one without reloading, and **All requests** shows the whole list. A request someone already answered, in Slack or anywhere else, says who answered it and how.

When your team routes a request to someone else, your own request says who it's waiting on, like "Waiting on Maya, on call". If nobody answers in time, it also goes to your admins.

Home's **Waiting for you** previews up to three of the same rows as the Inbox's **Waiting on you**, agent actions first and then any other requests waiting for you, with **See all N waiting** to open the rest. The badge next to **Inbox** in the navigation adds what needs attention to that count. A session that has ended never shows **Waiting for you**. See [Inbox](/member/inbox).

A request for a command your agent wants to run stays open for a day, whether or not someone was at the keyboard. A request for an app's tool asked in your agent's own prompt stays open for about three minutes. If your rules change while a request is waiting and would now run the action, the request resolves itself.

### When the agent stopped waiting

Agents don't wait forever: the guard holds for a few seconds, and an agent's turn can end or its session can close while a command waits for you. You can still approve that command for a day. The Inbox and your phone say so first: "The agent stopped waiting. Approving lets it run the next time the agent tries it." After you approve, it reads "Approved. The agent stopped waiting, so it will run the next time the agent tries it."

The approval is a one-time pass for that exact command in that agent session. It runs once, the next time the agent tries the same command there, and lapses a day after you approve. A different command, or another session, asks again. Passport never runs the command itself. A decline stays final.

For your own Claude Code session, the Inbox shows the command that resumes it, such as `claude --resume 0b5c…`, with a copy button. When the session resumes, or the next time you type in it, Passport tells the agent which command was approved, by whom, and when, once. Codex and Cursor don’t take that message: the approved command runs the next time the agent tries it.

### Learning from your approvals

When you approve the same command or tool in the same environment three times in two weeks, and haven't declined it there, Passport asks once: "You approved `gh workflow run` in Development 6 times this week. Always run it here?" It shows in the **Inbox** right after you approve, and as one quiet row in Home's **Needs attention**. **Always run** adds an exception just for you, for that command and environment only, which you can undo for 10 seconds or remove later in **Rules**; **Not now** waits for three more approvals, and **Don't suggest this again** is for good. Passport never suggests Production deletes or irreversible actions, or anything your team's floor keeps asking about.

## Agents you own

Your rules also govern the agents whose agent tokens you own. An agent can't answer a prompt, so its request waits in your **Inbox**, naming the agent that asked. An agent token with no owner is blocked from anything that would need a person: assign it an owner in **Agents**.
