---
title: "Backups and undo"
description: "Passport backs up what a delete removes, right before it runs, and can undo it for 7 days."
---

Open in Passport: [Work](https://passportmcp.com/#work)

When an agent deletes or overwrites something through Passport, Passport first saves what's about to go, where it can. For 7 days you can undo it: with **Undo** on the action's row on its task's page in [Work](/member/work#a-tasks-page), from the terminal, or by asking your agent.

Passport only backs up actions it can see: app tools, the production toolkit, and `passport exec`. A command an agent runs with a key on your computer gets no backup, which is one reason to [move your keys into Passport](/member/cli-hook). The exception is everyday deletes from the shell: see [Backups on your computer](#backups-on-your-computer).

## What Passport backs up

| App | Actions | The backup | Undo |
| --- | --- | --- | --- |
| GitHub | Deleting or overwriting a file, closing an issue or pull request, deleting a branch (`gh api` through `passport exec`) | The file's previous version (it stays in the repository), the issue's state, the branch's commit | Puts the file back as a new commit, reopens (first recreating a pull request's branch that closing it deleted, as the preview says), or recreates the branch. A merge can't be undone. |
| Vercel | `vercel env rm`, `vercel rollback`, `vercel promote` through `passport exec`, and `prod_rollback` | The variable's value and targets, or the deployment in production | Recreates the variable, or promotes the earlier deployment. Sensitive variables can't be read back, so they get no backup. |
| Railway | Setting variables, and `prod_rollback` | The variables' previous values, or the deployment that was running | Sets the old values (Railway redeploys), or rolls back to that deployment |
| Supabase | SQL that deletes, updates, or empties up to 5 tables of up to 1,000 rows, and pausing a project | A copy of those tables' rows, or the project's state | Restores the rows in one transaction, or restores the project |
| Neon | SQL that changes data or schema | A branch made from the target branch right before the SQL ran | Restores the branch from it and keeps the state it replaced as a branch for 7 days |

Not backed up: Railway volume, service, and environment deletes (Railway removes a volume's backups with it and can't restore the others), Neon branch deletes and resets, Supabase branch deletes and resets, and schema changes on Supabase. Irreversible actions never get a backup, because they can't be taken back even with one.

Variable values and table rows are encrypted and deleted after 7 days. Branches Passport made on Neon are removed after 7 days (Neon also expires them on its own), or as soon as you undo. Neon won't delete or reset a branch that has backups under it, so when you delete or reset one, Passport removes its own backups of that branch first and the action's row says how many.

## How backups change decisions

- **Ask only for irreversible:** a delete runs only once its backup is taken. If Passport can't take one, it asks you instead: "Couldn't take a backup first, so Passport is asking." This covers deletes an agent runs from the shell too: the ones Passport backs up on your computer run (see below), and others, such as `kubectl delete`, ask. To let those deletes run without a backup in Development, Staging, or Other apps, turn on **Run deletes Passport can't back up** under **Safeguards** in **Rules**. It's off by default, and it isn't offered for Production.
- **Ask before changes** and **Ask before deletes:** deletes ask as before. The request says whether Passport will take a backup right before it runs.
- A specific rule that always runs an action, or **For this task**, skips the ask, not the backup: Passport still takes one first wherever it can. When no backup was possible, it runs anyway.

## Backups on your computer

Right before an agent runs one of these from the shell, the guard keeps a backup on your computer, under your Passport folder, for 7 days:

| Command | The backup |
| --- | --- |
| `rm`, `rm -r`, `rm -rf` of files in the project or your home folder (Claude Code) | The files move to Passport's trash for this project instead of being deleted. They're gone from where they were, exactly as with `rm`. |
| `git reset --hard`, `git clean`, `git checkout -- …`, `git restore …` | Your changed and untracked files, saved as a git commit kept under a private ref. Your staged changes aren't touched. |
| `git stash drop`, `git stash clear` | The dropped stashes. |
| `git branch -d`, `git tag -d`, `git update-ref -d`, `git push --delete`, `git push --force` | The commit each branch or tag pointed at. A remote branch is saved as your computer last saw it, as of your last fetch or push. |

Folders a build or an install makes again need no backup: `rm -r` of `node_modules`, `dist`, `build`, `out`, `.next`, `.nuxt`, `.turbo`, `.cache`, `coverage`, `__pycache__`, `.pytest_cache`, `.gradle`, `target` (beside a `Cargo.toml` or `pom.xml`), `.venv` or `venv` (beside a requirements or `pyproject.toml` file), and `vendor` (beside a `composer.json` or `go.mod`) inside the project, or a `git clean -x` or `-X` that removes only what's inside them, runs and its row says **Regenerable, not backed up**. When git tracks any file inside such a folder, Passport treats it like any other folder and takes the usual backup. A `git clean -x` or `-X` that removes those folders and other ignored files too keeps a backup of the others only, runs, and its row says **Backed up (build folders not backed up)**; when the others are over the snapshot limit, it asks.

So with **Ask only for irreversible**, these run instead of asking. Passport skips the backup, and the command asks as usual, when it can't keep an exact copy: the line uses a pattern, a variable, `~`, a redirect, or more than one command; the path is outside the project and your home folder, in agent settings, or on another disk; it's a device or a mount point; or it's large (over 10,000 files or 512 MB for the trash, 5,000 files or 256 MB for git). Only Claude Code lets Passport move files to the trash, so in Codex and Cursor `rm` asks.

To see what was saved, and put one back:

```sh
passport undo --local
passport undo --local <id>
```

With an id, Passport shows what comes back and asks first. It never replaces something that's there now (a file you changed since, a branch at another commit, a remote branch) without asking about that one thing; without a terminal, add `--yes` and those are left as they are.

The files, refs, and commits never leave your computer. Passport only learns each backup's id, so **Undo** on the action's row says the backup is on your computer and shows the exact command to run there, with a copy button. If Passport is signed in on that computer, **Send to** your computer queues the restore: the next time you run `passport` in a terminal there, it shows what comes back and asks. Nothing is put back until you say yes at that terminal, never from an agent's shell, a script, or `--yes`. The row says **Sent to** your computer while it waits.

## Undo

**Undo** on an action's row first shows what comes back, what it replaces that's there now, what won't come back, and how old the backup is. Some things never come back: notifications and webhooks already sent, and anything other systems did because of the change.

If the thing changed again since, a plain restore would overwrite that change, so Passport offers a safe alternative instead where there is one, such as restoring a file as a copy, a variable under a new name, rows into a new table, or a Neon backup as a new branch.

The dialog shows how it went, step by step. The row then says **Undone**, **Partly undone**, or **Last undo didn't work**, and the last two keep **Undo** so you can try again. Undoing twice never restores twice.

After 7 days the backup is gone and the row has no **Undo**. Undo also isn't available while someone else is undoing it (the row says **Undoing**), or if you can't reach the app (connect it in Passport first). You can undo your own actions and those of agents you own; workspace admins can undo anyone's, with their own connection, and the person whose action it was gets an email saying so.

An undo is an action too, and most undos can be undone again. An undo you run from the web is your action, not the agent’s, so it’s in **History › Actions** rather than the agent’s task, and an ended task stays ended.

From the terminal:

```sh
passport undo --last
passport undo <action-id> --yes
```

Agents can call `passport_undo`. An undo from the terminal or an agent is decided like a change in that environment, so in Production it asks you first.

When your team needs someone else to approve Production deletes, the undo of a Production delete goes to them too, whether you start it in Passport, the terminal, or an agent. Undo again once they approve. See [Production approvers](/admin/slack-and-approvers#production-approvers).
