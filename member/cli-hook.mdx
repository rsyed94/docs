description: "Let Claude Code, Codex, and Cursor report the command-line tools they reach for, and ask before the ones that delete or can't be undone."

Your agents do plenty of work that never goes through Passport: `gh pr create`, `git push`, `railway up`, `kubectl delete`. The Passport hook puts that work in the same audit log as everything else your agents do. With the guard on, Passport also applies your Autopilot rules to the commands it recognizes.

## Turn it on

```sh
passport hook install --agent claude-code --guard --apply
```

Use `--agent codex` or `--agent cursor` for those agents (`--client` still works). Leave out `--guard` to only record commands. Without `--apply` you see exactly what would change and nothing is written.

| Agent       | File                      | Before a command (guard) | After a command (audit)             | Session start and end         |
| ----------- | ------------------------- | ------------------------ | ----------------------------------- | ----------------------------- |
| Claude Code | `~/.claude/settings.json` | `PreToolUse`             | `PostToolUse`, `PostToolUseFailure` | `SessionStart`, `SessionEnd`  |
| Codex       | `~/.codex/hooks.json`     | `PreToolUse`             | `PostToolUse`                       | `SessionStart`                |
| Cursor      | `~/.cursor/hooks.json`    | `beforeShellExecution`   | `afterShellExecution`               |                               |

Passport adds only its own entries and leaves your other hooks alone. Codex asks you to trust new hooks: open Codex → `/hooks` and trust Passport's hooks.

Check what is registered:

```sh
passport hook status
```

```
Claude Code  Audit and guard · On           ~/.claude/settings.json
Codex        Audit and guard · Not trusted  ~/.codex/hooks.json
Cursor       Audit · Off                    ~/.cursor/hooks.json

Autopilot rules: synced 12 minutes ago.
Codex can't show Passport's questions, so Passport blocks a command your rules ask about and tells you how to approve it.
Codex: Open Codex → /hooks and trust Passport's hooks.
Cursor: Turn the guard on.
Run: passport hook install --agent cursor --guard --apply
```

## Guard health

Each agent on each computer has one guard state, the same on the **Agents** page, a person's page, Home, the alerts bell, the weekly email, and in `passport status`:

| State       | What it means                                                                            | Fix                                                     |
| ----------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| On          | The guard reads every shell command before it runs.                                      |                                                         |
| Locked      | Managed settings your company set keep the guard on.                                     |                                                         |
| Off         | The agent is installed but the guard isn't registered, or it was turned off.             | `passport hook install --agent <agent> --guard --apply` |
| Outdated    | The Passport CLI on that computer is too old to read commands the way your rules expect. | `npx passport-bridge@latest init`                       |
| Not trusted | Codex hasn't trusted Passport's hook in `/hooks`, so Codex doesn't run it.               | Open Codex → `/hooks` and trust Passport's hooks.       |

The Passport CLI reports these at most once a day: from a hook with time to spare, from `passport exec`, and from `passport status`. It sends flags only, never a command, a path, or a setting's value. For Codex it compares the hash Codex stored for Passport's hook in `~/.codex/config.toml` with the hook as written, the way Codex itself decides whether to run it. A report is your computer's own word, so treat it as visibility, not proof. A computer that keeps working but stops reporting for a week reads **Not reporting**.

When an agent's guard turns off after being on, goes out of date, or isn't trusted, the person and workspace admins get an alert in the bell, linking to the agent. It clears itself once the fix is in.

## Decided, placed, and blind

Passport counts what the guard saw on each computer, per agent and per day, and sorts every command into one of three buckets:

- **Decided**: Passport recognized every part, so your rules could answer it, such as `git status` or `railway up --environment staging`.
- **Placed**: Passport knows what kind of action it is and where it lands, but can't allow it, such as the project's own scripts (`node scripts/build.mjs`, `make test`, or a package script that runs them) or a vendor command with a variable in it.
- **Blind**: Passport couldn't tell what it does: a program it doesn't know, a script outside the project, a package it doesn't know, SQL from a file (`psql -f`), or a one-liner (`node -e`, `python -c`).

Each agent row on **Agents**, each person on **People**, each team, **Agents → Rollout**, and Home show the share your rules could decide over the last week, such as "decides 82%". An agent's page also names the three programs it was most often blind to, such as "Not checked: python3 ×12, node ×3". A session shows its own counts, such as "468 checked · 12 not checked · 3 could reach Production". `passport status` prints the week's line. Computers on a CLI before 0.24.0 don't sort their commands: what they couldn't read counts as not checked, and their rows show "468 checked · 12 not checked" instead of a share.

When a session that changed confirmed Production had blind commands, the agent's owner and admins get an alert, at most once a week per computer, and the weekly email has a Coverage section. Open the agent's [sessions](/member/sessions#what-passport-saw) to see what Passport couldn't tell.

## What the guard does

Before each shell command, the guard reads it on your computer and decides from your Autopilot rules, the same rules your apps follow in Passport, so a command and a tool that do the same thing get the same answer. It works out the environment the way the vendor's own CLI does: a flag first, such as Railway's `--environment` or Vercel's `--prod`, then the folder's link, then the vendor's default. A linked environment nobody has placed yet is read by the name your connected app gives it, so a Railway environment called `staging` is Staging; the name in a link file on your computer never counts. A command with no environment it can place counts as Production. See [how Passport knows](/member/safety#how-passport-knows).

When a rule says to ask first, your agent asks you, with the reason:

```
Passport: railway redeploy changes Production (linked in this folder). Approve to run it.
```

### See what a folder is linked to

```sh
passport env
```

```
App      Resource      How     Environment
Railway  production    linked  Production (from its name)
Vercel   web preview   linked  Staging
Fly      shop          linked  Production (assumed)
Fly shop: Not placed yet, so Passport treats it as Production.
```

"From its name" means Passport placed it by the name your connected app gave it; "assumed" means there is no such name yet, or it says nothing, so it counts as Production until you place it. In a narrow terminal each row is shown on two lines instead of columns.

Passport reads Railway, Vercel, Supabase, Wrangler, Netlify, Firebase, Convex, Neon, Fly, Heroku, kubectl, AWS, gcloud, Terraform, and Stripe links, plus database URLs for `psql`, `pg_dump`, Prisma, drizzle-kit, Knex, Sequelize, Rails, and Alembic. Everything is read on your computer each time a command runs; only an id-style key and how it was found reach Passport, never a path, URL, or key. A folder with nothing linked shows "No linked apps in this folder."

If Passport guessed wrong, fix it once for the whole workspace:

```sh
passport env set railway qa staging
```

Admins can choose any environment. Everyone else can only say Production, and gets "Ask an admin to place it" otherwise.

When a rule blocks it, the command doesn't run:

```
Blocked by a team rule: no deletes in Production. Ask an admin to run it, or request an exception in Passport.
```

When nobody is at the keyboard, such as in CI or a background agent, an ask becomes an approval request on the web and your phone, and the agent can run `passport wait <id>`. A decline answers the same command for ten minutes, so the agent hears "Declined 2 minutes ago by Erin" instead of asking you again; `passport exec --ask-again` requests it anew. `passport login` and `passport status` sync your rules to your computer, and the guard refreshes them in the background about once an hour. Signed out, it asks before every command it recognizes as a Delete or Irreversible. Change your rules any time in **Rules**; `passport status` prints a link to it.

A command the guard doesn't recognize, or one it can't read with confidence (scripts, aliases, `make` targets, a path in a variable), runs through your agent's usual permissions.

## Everyday commands

Your agent's own work in the project folder counts as **Development**, so with the default Hands-off preset it runs without a prompt: tests, builds, linters, formatters, package scripts, `git commit`, and deletes Passport backs up first, such as `rm -rf build` (Claude Code), `git reset --hard`, or `git branch -D`; see [Backups on your computer](/member/undo#backups-on-your-computer). Deletes Passport can't back up ask unless you turn on **Run deletes without a backup** for Development. The project folder is the repository root, or the folder your agent works in.

| Command                                             | Counts as                                                      |
| --------------------------------------------------- | -------------------------------------------------------------- |
| `npm test`, `rg TODO`, `git status`, `tsc`          | Read in Development                                            |
| `git commit`, `prettier --write .`, `npm run dev`   | Change in Development                                          |
| `rm -rf dist`, `git reset --hard`, `git clean -fd`  | Delete in Development                                          |
| `npm install`, `pip install`, `brew install`        | Change on this computer, decided as Other apps                 |
| `git push` to your branch, `gh pr create`           | Change in Development                                          |
| `gh pr view`, `gh run view`, `git fetch`            | Read, no environment                                           |
| `git push origin main`, `gh pr merge`               | Change in Production until you place the repository            |
| `git push origin --delete old-branch`               | Delete in Other apps (teammates share it)                      |
| `rm -rf /tmp/scratch`                               | Delete in Development (temporary folders count as Development) |
| `curl https://…`                                    | Read in Other apps (sending data is a Change)                  |
| `rm -rf ~/`, `rm -rf /`, deleting the whole project | Irreversible, always asks                                      |
| `sudo …`                                            | Always asks                                                    |

Symlinks count where they point, `cd` inside a command is followed, and writing to your keys or shell startup files counts as a delete. Try any command on the **Rules** page or with `passport rules test "npm test"`.

Code that reaches a repository's default branch only reaches people if that repository deploys when you merge. The first push to a repository's default branch shows it in **Rules → Environments**, treated as Production until you choose: keep **Production** for a repository that deploys on merge, or choose **Staging** for one that doesn't. A force push to it asks either way, because Staging asks before deletes.

## Fewer prompts, even offline

```sh
passport sync
```

Passport adds the commands your rules run without asking to each agent's own allowlist, so those prompts stop even when Passport can't be reached, and in Codex, which can't take an allow from a hook. Only tests, builds, type checks, checks that don't change files, `git status`, `git add`, and `git commit` are added. Formatters, package scripts, and file moves stay with the hook, and deletes, installs, and anything in Production never are.

| Agent       | Where                                                                           |
| ----------- | ------------------------------------------------------------------------------- |
| Claude Code | `permissions.allow` in `~/.claude/settings.json`                                |
| Codex       | `~/.codex/rules/passport.rules`                                                 |
| Cursor CLI  | `permissions.allow` in `~/.cursor/cli-config.json`                              |
| Cursor      | `terminalAllowlist` in `~/.cursor/permissions.json`, only if you keep one there |

Your own entries are never changed. Passport updates its entries when your rules change, and `passport sync --remove` or `passport hook uninstall` takes them out. `passport status` shows how many prompts Passport answered for you today.

<Note>
  Codex can't ask from a hook (an ask there would let the command run). So in Codex, a command your rules ask about is
  blocked, the approval request comes to you in Passport, and the agent can run it again once you approve.
</Note>

## When Passport can't be reached

Most decisions happen on your computer from rules synced in the last hour, and those stand as decided: a command that runs still runs, a block still blocks, and when you're at the keyboard you answer the ask yourself. Only an ask that needed Passport (an unattended run, Codex, or a Production action someone else approves) uses each environment's setting on the **Rules** page when Passport doesn't answer in time: **When Passport can't be reached: Ask, Block, or Run**. Every environment asks unless you change it.

- Nobody can answer an ask for an unattended agent or Codex, so Ask blocks there, with one line saying why.
- An action someone else must approve is blocked, since nobody can approve it offline.
- Run is only ever your own choice. It never covers an irreversible action, and never loosens what your team requires: a team floor, a team or workspace rule, an approver rule, or an approved exception still asks (so an unattended agent is blocked).
- Rules synced more than 7 days ago fall back to the built-in setting (Ask).

## App access

Your access to an app in Passport covers its CLI too. If you have **No access** to Railway, every `railway` command an agent runs through the guard or `passport exec` is blocked with `You don't have access to Railway in Passport. Ask an admin.` and a link to the app's **Access** tab. **Read-only** access runs only commands that read; anything that changes or deletes is blocked, saying so. A CLI whose app isn't in your workspace works from its key, as before. This covers the CLIs `passport exec` runs: `railway`, `gh` (GitHub), `vercel`, `wrangler` (Cloudflare), `supabase`, `stripe`, `aws`, `neonctl` (Neon), and `flyctl` (Fly.io).

AWS has no MCP server to connect, so an admin adds **AWS** from the catalog as a CLI app: no sign-in and no tools, just who may run `aws` and how. Its **Tools** tab lists common commands by class. Reads such as `aws s3 ls` run; changes follow your rules; commands that open access (`iam attach-role-policy`, `s3api put-bucket-policy`) ask like a delete; and terminating an instance or deleting a bucket, table, or database in Production is **Irreversible**. The **AWS Knowledge** docs app is a separate app and never decides who may run `aws`.

## Keys in Passport

Move a CLI's sign-in into Passport, and agents run that CLI through Passport instead:

```sh
passport keys move
passport exec -- railway up -e staging
```

`keys move` asks about each key (`[y/N]`, so Enter keeps it), stores it in Passport, and signs that CLI out on your computer. `passport keys move railway` moves only that one. If Passport already holds a different key for that CLI, every agent that uses it would switch, so you type the CLI's name to replace it (`Type railway to confirm, or press Enter to cancel:`); anything else keeps the key in Passport and leaves this computer signed in. Only you, at a terminal, can replace a key: with `--yes` or without a terminal nothing is replaced, and `keys move` says `Replacing a key in Passport needs you at a terminal.` and `Run: passport keys move railway`. A replacement alerts you and your admins ("Railway key in Passport was replaced from Laptop by Maya. Undo."), is in the audit trail, and can be undone for seven days from the alert or the app's **Keys** tab. Signing out removes only the key: your project links, current team, profiles, and other settings stay. `.env` files stay as they are, since your apps need them. `passport exec` asks Passport before each command; when your rules allow it, the key reaches only that command, short-lived for GitHub (with the GitHub App installed), AWS, and Cloudflare where the key allows it. In Claude Code, the guard sends commands for those CLIs through `passport exec` for you. If Passport can't be reached, nothing runs.

Each key lives on its app. In **Apps**, the app's row says **Key in Passport**, and flags one that stopped working or is back on a computer. Open the app and its **Keys** tab to rotate or remove your key; admins also see who keeps a key for that app, whether it works, and when agents last used it, never the key itself. A key for a CLI whose app isn't in your workspace stays listed under your apps, with any computer that still holds keys.

### Rotate a key

Each key's row says how old it is ("Added 120 days ago"). When a key gets older than your workspace allows (90 days unless an admin picks another time in **Settings › Access › Keys in Passport**), or a data check catches its value in a tool call, **Home** shows one line under **Needs attention**, like "Your Railway key is 120 days old. Rotate it.", with a **Rotate** button.

**Rotate** (on Home, or on the key's row) opens three steps:

1. **Make a new key** at the provider. The dialog links to the exact page, such as Railway's account tokens or GitHub's personal access tokens.
2. **Paste it.** The field is masked, and Passport never shows the value again. Passport checks the new key with one harmless read at the provider, like asking who the key belongs to. Only if that works does it replace the old key, in one step. If the provider refuses it, or Passport can't reach the provider, your old key stays exactly as it was.
3. **Revoke the old key** at the provider, with the link to that page. Choose **Done** once you have, and Passport records it. Until then, the key's row reminds you.

From a terminal:

```sh
passport keys rotate railway
```

It shows where to make the new key, asks for it without showing what you type, checks it the same way, and prints where to revoke the old one. It only runs with you at the terminal, never from a script. After a rotation from the CLI, the old key stays restorable from the key's row for seven days, and you and your admins get an alert.

Admins see how old each person's keys are, and which need rotating, on the app's **Keys** tab and in **People**, on the person's **Apps** tab. They never see a key, and only its owner can rotate it. Each rotation is in the audit trail: who, which app, and when, never the value.

### Keep typing the CLI yourself

Once a CLI is signed out, typing `railway up` on its own would fail. So after each key it moves, `keys move` asks `Keep typing railway in your terminal? Passport runs it with the key it now holds. [Y/n]`. Yes (or Enter) adds a small `railway` command to Passport's folder, `~/.passport/cli/bin`, that runs `passport exec -- railway` with what you typed. `--yes` adds them without asking, and `--no-shim` leaves them out.

```sh
passport keys shim                   # list them, and whether your terminal uses them
passport keys shim railway           # add one for a key you stored with keys add
passport keys shim --remove railway  # take one out (or --remove all)
```

Your shell has to find Passport's folder before the vendor's own CLI. If it doesn't, Passport prints the one line to add to your shell profile (the same line `passport init` prints); it never edits the file itself. Open a new terminal afterward. `passport status --json` lists the shims under `shims`.

The shim never runs itself: `passport exec` always runs the vendor's own CLI, skipping Passport's folder. A shim goes away by itself when Passport no longer holds that key (so the CLI runs on its own again) and when you sign out of your last profile.

### Keys never show in the output

When the output isn't going to a terminal (an agent's shell, a pipe, a CI log), `passport exec` reads the CLI's output and error streams. It replaces every copy of the key it handed out, raw, base64, or URL-encoded, with `<hidden by Passport>`, like `op run`. That output is what gets saved in transcripts and logs and read later, so that's where a printed key does harm. Output still streams line by line, and the exit code is the CLI's own (or 128 plus the signal that stopped it).

In a terminal, the CLI gets the terminal itself, so colors, prompts, and progress bars work as usual, and nothing is masked: you're watching your own screen. To mask there too, add `--mask`. The CLI then writes to Passport instead of your terminal, so its output may come out plainer. `--no-masking` (or `PASSPORT_EXEC_NO_MASKING=1` through a shim) turns masking off everywhere.

### Keys back on a computer

After a move, the CLI remembers where each key was (the file, the field names, the file's size and time, never a value or a hash of one). Once a day it checks those files, and if a key Passport holds is back on that computer, the key reads **Back on &lt;computer&gt;** on its app's **Keys** tab and row in Apps, with an alert: "A Railway key is on Priya's MacBook Pro again." The fix is the same move: `passport keys move`. Once the key is gone again, by either route, the next daily check clears it.

Keys usually come back because a CLI was signed in again. While Passport holds a working key for that CLI, the guard answers an agent's `railway login` (in Claude Code, Codex, and Cursor) with "Passport holds your Railway key; run it through Passport", and so does the shim when you type it. `keys move` also signs out a browser sign-in Passport can't hold itself (Railway, Vercel, Wrangler) when it already holds a working key for that CLI.

The first time `keys move` runs at a terminal, it asks once: **Keep my CLIs signed out?** With yes, the daily check removes a key that came back on its own, while Passport holds a working key for that CLI, and nothing shows up for you to fix. Change the answer with `passport keys signed-out on` or `off`.

### Keeping a CLI signed in on purpose

Some commands need the CLI signed in on your computer: local dev loops like `railway run`, `vercel dev`, and `supabase functions serve`. `wrangler dev` runs through `passport exec` with a 15-minute Cloudflare key when yours can mint one. For the rest, keep that CLI signed in on purpose:

```bash
passport keys keep railway            # signed in here for dev and releases
passport keys keep railway --remove   # back to normal
```

A kept CLI signs in as usual, Passport never removes it, and it isn't counted as a key left to move. Its shim is removed, so typing `railway` runs the CLI directly. The computer that releases Passport itself keeps its Railway key this way automatically.

## Guard required

On Pro, an admin can require the guard for a team in **Rules › Team rules**. With **Required**, `passport exec` runs only for an agent whose computer reported its guard On (or Locked) in the last 48 hours; otherwise the command stops with "Blocked by Passport: guard required" and the fix, and its session row reads **Blocked · Guard required**. **Report only** shows those agents on **Agents** without stopping anything. Tools your agents call through Passport are always checked by Passport itself, so this applies to `passport exec`.

## Speed

Passport should never slow your agents down. Plain reads and local checks, such as `ls`, `cat`, `rg`, `git status`, `git diff`, `cargo check`, and `pytest`, are answered by the `passport` launcher itself in about 10 ms, without starting Node, whenever your rules would answer them the same way anyway. Anything else, or any doubt (another program in a pipe, a redirect, a path outside the project, a symlink, a hidden file), gets the full guard. After a command, the hook queues its report and returns at once; it never waits on the network.

`passport status` and Home show what Passport cost you today:

```
Passport adds ~20 ms per action and asked you twice today. 412 actions ran on their own.
```

Only numbers leave your computer for this: how long each check took, whether it asked, and how long you took to approve. Never a command or a folder.

## Scripts

When an agent runs the project's own code, the guard reads what it runs and decides from that:

- `./deploy.sh`, `bash deploy.sh`, and `source env.sh`: every line of a shell script
- `make deploy`: the target's recipe, after its prerequisites, with the Makefile's variables filled in once
- `npm run deploy`, `npm test`, `pnpm deploy`, `yarn deploy`: the package script, with its `pre` and `post` scripts

Each line is decided like a command you typed, and the strictest one wins. `./deploy.sh` that runs `railway up --environment production` asks first, and says where it came from: "Passport: railway up changes Production (from --environment, in deploy.sh)." In **Sessions**, that row reads `railway up · from deploy.sh`.

A script the guard can follow to the end, every line understood, is **checked**. One it can't (a line with a variable it can't resolve, a `case`, a program it doesn't know, more than 256 KB, more than 30 ms of reading) is **Partly checked**: risky lines it did recognize still ask or block, but it never runs on Passport's say-so. In a command with several parts, each part is checked on its own, such as "1 checked · 1 partly checked". After the command, the hook reads the script again; if it changed in between, the row says **Changed after the check**.

Python and JavaScript files aren't read yet. Tell Passport what one does instead (below).

### Tell Passport what a script does

From a **Partly checked** or **Not checked** row in **Sessions**, choose **Tell Passport what this does** (the first row for each program offers it; open any other row to find it there), or run:

```sh
passport actions add scripts/deploy.py --environment production --class change
passport actions add make seed --environment staging --class delete
```

Passport then checks that script as a Change in Production (or whatever you said), with your presets and exceptions deciding as for any command. A project script never runs on its own say-so. You can say Production for a change, delete, or irreversible script; anything looser waits for an admin in **Rules › Environments › Project scripts**. When the script changes, the row there says **Changed since set** and the guard reads it again until someone sets it.

A repository can keep its own list in `.passport/actions.toml`:

```toml
[[action]]
script = "scripts/deploy.py"
environment = "production"
class = "irreversible"
```

On its own, the file can only make things stricter: the guard uses an entry when it asks or blocks, never when it would run. `passport actions sync` proposes every entry to your workspace.

## What it can't see

The guard is a guardrail, not a security boundary. Aliases, shell functions defined elsewhere, and code in other languages are beyond it. `--help` and `--dry-run` never trigger it.

## What it records

After each shell command, the hook sends Passport only:

- the tool that ran, such as `gh` or `terraform`
- a coarse verb, such as `pr create` or `apply`
- for everyday commands, where they landed (Development, Other apps, Production), never a path. Allowed work in your project is only counted, not recorded one by one
- what kind of command it was: read, write, destructive, api, sql, http, or unknown. Passport shows it as one class: Read, Change, Delete, or Irreversible
- whether the command succeeded, how long it took, and the name of the folder you were in
- your agent's session identifier, so a run hangs together, and when the session starts and ends, with the model's name and whether someone is at the keyboard when the agent says so
- when the guard stepped in, whether it asked first or blocked the command
- counts of the commands the guard saw, by bucket, and the name of the program behind each blind command (`python3`, never a path or a script's name)
- for a command read from a project script, the script's name (`deploy.sh`, `make deploy`), how many parts were checked or partly checked, and for a part it couldn't check, a hash keyed with a salt that never leaves your computer, so Passport can suggest telling it what that script does
- for Claude Code sessions, token numbers: see [Token usage](#token-usage)
- only if an admin turns on **Show what agents say they're doing** (off by default), and only from Claude Code: the agent's own one-line description of the command, such as "Run the bridge tests"

The description is redacted on your computer before it's queued. It becomes one line of at most 80 characters, a path becomes its last name (`cliHook.ts`), and a link becomes its host. If it contains anything the approval summary would hide, such as a key, a token, or a long opaque value, or an email address, nothing is sent at all. Other agents don't give a description, so they send none. Passport keeps it with the activity row for 90 days, shows it as the row's label in Sessions, and uses the first change's description as the session's goal. Turning the setting off stops Passport keeping new ones right away and hides the ones it kept.

Each finding becomes one activity row under its app, such as **GitHub CLI** or **Git**, with everyday commands under **Shell**. The action reads like "railway redeploy". A blocked command shows as blocked. In Claude Code, a command Passport asked about is one row: "asked first, then ran" if you approved it, or "asked first, not run" about 30 minutes after you declined it. In Cursor, the ask and the run are separate rows.

## Token usage

For Claude Code sessions, Passport shows how many tokens a session used and its **API-equivalent cost**: what those tokens would cost at Anthropic's API list prices. It's an estimate, not what you paid; a Claude subscription or a company plan is priced differently. Sessions show it in the summary, work items on **Sessions** add up their sessions, and Home shows the week's total.

To get the numbers, `passport hook flush` (which runs in the background, never while your agent waits) reads the session's transcript file on your computer, the one Claude Code keeps under `~/.claude/projects/`, including its subagents' files. It keeps only the input, output, cache-read, and cache-write token counts of each reply and the model's name, and sends those with the session's identifier. It never sends, and Passport never stores, what was said, tool calls, or file contents; lines without token numbers aren't even parsed. It remembers how far it read each file in `~/.passport/usage/`, readable only by you.

A model Passport has no price for shows tokens only. Codex and Cursor don't give hooks token numbers, so their sessions show none.

It's on by default. An admin turns it off for the workspace in **Settings → Workspace** (**Token usage per session**). To turn it off on one computer, set `PASSPORT_TOKEN_USAGE=off` in the environment your agent runs in.

## What it never records

The hook never sends, and Passport never stores:

- the command line or any of its arguments (a description, when it's on, is the agent's words about the command, never the command)
- the command's output
- your full folder path, only the last folder name
- anything from your environment, including tokens
- anything from an agent's transcript but token counts and the model's name

The guard decides on your computer before anything reaches the network. It reads project scripts on your computer and never sends what they contain; results are cached in `~/.passport/scan-cache.json`, readable only by you. A script it can't read sends its shape and a hash keyed with a random salt made on your computer, kept in `~/.passport/opaque-salt` (readable only by you), and never sent, never its name. Passport can't work backward from that hash to a name, so a suggestion to tell Passport what a script does counts runs per computer. `passport actions add` sends the script's path in the repository, a fingerprint of the repository's remote, and a hash of the script.

## Turn it off

```sh
passport hook uninstall --agent claude-code --guard --apply   # guard only
passport hook uninstall --agent claude-code --apply           # guard and audit
```

This removes only Passport's entries. To pause both for one session instead, set `PASSPORT_HOOK_DISABLED=1`.

See also [Activity and audit](/admin/activity-and-audit).
