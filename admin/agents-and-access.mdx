Open in Passport: [Rules › Team › Which agents can connect](https://passportmcp.com/#rules/team?section=agents)

Connect your AI from [Agents](https://passportmcp.com/#agents). Claude Code, Codex, Cursor, and other supported agents use your Passport connection and its permissions. Agents and subagents using the same sign-in share that access boundary; Passport does not require a separate identity for each one. Admins choose which agents can connect in **Rules › Team › Which agents can connect**, and **Workspace safety** at the top of **Rules** shows that choice with the other policies that apply to everyone.

Connect a company account on its app's **Sign-in** tab. People request access from the app's page in **Apps**, admins answer those requests in the [Inbox](/member/inbox), and actions that require consent wait there too.

Company access requires Enterprise workspace controls and PostgreSQL. The GitHub organization connection supports repository details, issue lists, individual issues, issue creation, and issue comments.

## Connect an organization

1. Create a GitHub App and install it on the repositories you want Passport to govern. Give it the repository permissions needed for your selected actions: metadata read, and issues read or write.
2. In [Apps › Manage workspace](https://passportmcp.com/#apps/workspace), open the GitHub app and its **Sign-in** tab. Under **Shared provider accounts**, enter the GitHub App ID and installation ID, then choose its private PEM file.
3. Preview the installation, select specific repositories, and create the connection.

Passport verifies the selected repository IDs and encrypts the private key. It requests short-lived installation tokens scoped to the particular repository and permissions needed for each invocation. The private key and provider tokens are never given to the agent.

## Request company access

Open the company account in **Apps** and request the actions and repositories you need, with a purpose and expiry. Admins answer these requests in the **Inbox**, and see them on the GitHub app's **Sign-in** tab. An approval cannot override an explicit block or an unavailable connection.

Your existing Passport sign-in exposes approved company tools alongside your personal tools. Each agent's app selection can narrow your access further.

## Approvals and activity

A grant can require approval for each action. Review the proposed action in the **Inbox**. Passport checks the current permission and records the outcome. Open **Sessions › All activity** to review your own work or, as a Pro or Enterprise admin, switch it to **Everyone** for the whole workspace. On Enterprise, once managed runs exist, a **Runs** tab beside the log holds durable action receipts and their approval history.

Standalone managed identity setup has been retired. Existing Activity is kept. For scripts and CI using Passport CLI, see [Automation credentials](/admin/people-and-teams#automation-credentials).

## Agent tokens, their owners, and rotation

An agent token is a credential a person owns, not an account of its own. The person who creates a token owns it, and that ownership decides three things.

**Approvals.** The owner's [Autopilot rules](/member/safety) govern the agent. An agent cannot answer a prompt, so a call that needs consent returns a pending result immediately and waits in the owner's **Inbox**, where the row names the agent that asked. When the owner decides, the agent's next attempt at the same call goes through. A decision is bound to the agent that asked: allowing one agent's action never releases an identical call from another. Tokens created before Passport recorded ownership keep their previous behaviour until they are rotated.

**Rotation.** Rotating a token mints a replacement, shows it once, and stops the old one. The agent identity, its access, and its Activity stay as they were, and no seat is used, because rotation creates no new person. An agent can hold up to five live tokens, so a rollout can overlap: `POST /api/agent-keys/:id/rotate` accepts `overlapMinutes` (up to 60) to leave the replaced token working while your jobs pick up the new one.

**Deletion and deactivation.** Deleting a token ends that credential. Deleting an agent's last token retires the agent identity and frees its place (Free includes 3 automations); the agent's page says which of the two a revoke will do. Deactivating a person, removing them, or signing them out everywhere revokes every agent token they own, and the gateway refuses a token whose owner is no longer active. Their agents need new tokens after that, so reassign long-lived automation before deprovisioning its owner.

An agent's owner stops, rotates, revokes, or adds tokens on its page in [Agents](/admin/client-fleet#an-agents-page) without an admin. **Stop** refuses every call the agent makes until someone resumes it; its tokens and rules stay as they are.
